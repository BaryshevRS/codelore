# writeGenerationDebug

## Зачем это нужно

Атомарная запись отладочного JSON-файла с данными о генерационном прогоне.

## Что делает

Не валидирует входные данные и не обрабатывает ошибки файловой системы — исключения пробрасываются вызывающему.
Вычисляет целевой путь отладочного файла на основе `statePath` и необязательной `phase`.
Создаёт родительскую директорию при необходимости.
Осуществляет атомарную запись: сначала во временный файл с уникальным именем, затем переименовывает в целевой путь.

## На что можно положиться

Путь отладки вычисляется исключительно по `statePath` через [`generationDebugPathForStatePath`](#generationdebugpathforstatepath).
Файл записывается только после создания всех родительских директорий.
Запись выполняется атомарно: сначала во временный файл, затем переименование.
Сериализация: `JSON.stringify(entry, null, 2) + '\n'`, кодировка UTF-8.
Возвращаемый `debugPath` всегда совпадает с путём, вычисленным [`generationDebugPathForStatePath`](#generationdebugpathforstatepath).

## От чего зависит

[`generationDebugPathForStatePath`](#generationdebugpathforstatepath) (`src/llm/generation-debug.ts`) — вычисляет путь отладочного файла на основе `statePath` и необязательной `phase`.

## Кто и как использует

Вызывается из `file-pipeline.ts` для сохранения отладочной записи генерационного прогона. Вычисляет целевой путь через [`generationDebugPathForStatePath`](#generationdebugpathforstatepath), создаёт родительскую директорию, записывает сериализованный `GenerationDebugEntry` во временный файл с уникальным именем (PID + случайная строка), затем переименовывает для атомарности. Возвращает `{ debugPath }`.

## Чего не делает

Не обрабатывает ошибки ввода-вывода (диск заполнен, права доступа) — исключения пробрасываются вызывающему.
Потокобезопасность не гарантируется: параллельные вызовы с одинаковым `statePath` приведут к гонке записи.
Формат файла (JSON с отступом 2 и завершающим переводом строки) является контрактом для читающих инструментов.

## Как менять и что проверять

1. Удаление атомарной записи (прямая запись) приведёт к тому, что читатель может прочитать неполный файл — проверить всех потребителей в `file-pipeline.ts` и скрипты, читающие `.generation-debug.json`.
2. Изменение форматирования JSON (отступы, trailing newline) сломает инструменты, которые парсят эти файлы по сигнатуре `JSON.parse`.
3. Изменение пути через [`generationDebugPathForStatePath`](#generationdebugpathforstatepath) требует синхронизации с этой функцией — её документация описывает контракт преобразования.
4. Если добавить обработку ошибок и изменить возвращаемый тип (например, `Promise<{ debugPath } | null>`), придётся обновить все места, где результат деструктурируется (см. `directUsages`).

# generationDebugPathForStatePath

## Зачем это нужно

Преобразование пути состояния в путь отладочного файла с заменой расширения `.json` на отладочный суффикс с учётом фазы.

## Что делает

Не обращается к файловой системе.
Не валидирует путь.
Заменяет только завершающий суффикс `.json` в конце строки.

## На что можно положиться

Если `statePath` заканчивается на `.json`, возвращается строка с заменой `.json` на отладочный суффикс.
Если не заканчивается, возвращается без изменений.
Функция чистая — не зависит от глобального состояния и не мутирует входные данные.

## Кто и как использует

Вызывается из [`writeGenerationDebug`](#writegenerationdebug) (тот же файл) для вычисления целевого пути отладочного файла. Заменяет суффикс `.json` в конце `statePath` на отладочный суффикс (учитывая необязательную `phase`).

## Чего не делает

Не обрабатывает пути, не заканчивающиеся на `.json` — возвращает без изменений.
Замена только суффикса `.json` в конце строки, не заменяет `.json` в середине.
Регистрозависима (не заменит `.JSON`).

# buildGenerationDebugEntry

## Зачем это нужно

Создание сжатого отладочного среза генерационного прогона для записи в `.generation-debug.json`.

## Что делает

- Копирует поля `runId`, `timestamp`, `command`, `provider`, `model`, `docPath`, `files` без изменений.
- Преобразует `sections` и `dependencyDocs` в сокращённое представление (идентификаторы, размеры). Оригинальное содержимое не сохраняется.
- Делегирует вычисление статистики текста LLM-этапов внутренней функции `mapLlmStages`.
- Включает необязательные поля `violations`, `violationsAfterRepair`, `error` только при наличии непустых значений (для массивов — если длина > 0).

## На что можно положиться

- Поле `version` всегда равно 4.
- `writtenBlocks` и `keptBlocks` всегда присутствуют в результате (при отсутствии во входе — пустой объект и пустой массив).
- `sections` и `dependencyDocs` всегда массив — даже если входные массивы пусты.
- Все обязательные поля результата всегда присутствуют (перечислены в типе `GenerationDebugEntry`).

## Кто и как использует

Вызывается из `generateFileGroup` ([`src/llm/file-pipeline.ts`](file-pipeline.codelore.md)) после обработки всех чанков каждого файла. `llmStages` наполняется через `debugSink` в процессе генерации. Результат передаётся в [`writeGenerationDebug`](#writegenerationdebug) для сохранения в `.generation-debug.json`.

## Чего не делает

- Не проверяет структуру объектов в `llmStages` — пустая запись или отсутствие поля `messages` вызывает необработанное исключение в `mapLlmStages`.
- Поля `dependencyDocs.chars` вычисляются через `JSON.stringify(doc.sections).length`, что может не соответствовать точному числу символов в исходных секциях (из-за сериализации).
- Опциональные поля включаются по условию `length > 0`, а не по наличию свойства — пустой массив `[]` исключается, что может быть неочевидно для вызывающего (если требуется явно указать «без нарушений»).
