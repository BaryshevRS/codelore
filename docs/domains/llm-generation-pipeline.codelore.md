# Пайплайн генерации документации файлов

## Состав

- [file-chunks](../../src/llm/file-chunks.codelore.md) — Разбивает набор исходных файлов и секций документации на чанки, каждый из которых помещается в контекст одной LLM-генерации с учётом лимитов токенов и числа секций, заданных через WriterBudget.
- [file-pipeline](../../src/llm/file-pipeline.codelore.md) — Точка входа для LLM-генерации документации группы файлов: загружает контекст, разбивает на чанки, выполняет запросы с валидацией и ремонтом, собирает результат.
- [file-writer](../../src/llm/file-writer.codelore.md) — Упаковывает исходный код, секции документации и dependency docs в структурированный запрос для LLM.
- [generation-debug](../../src/llm/generation-debug.codelore.md) — Атомарная запись отладочного JSON-файла с данными о генерационном прогоне.

## Зачем это нужно

Пайплайн генерирует документацию для группы изменившихся файлов за один прогон: разбивает исходный код на чанки с учётом лимитов LLM, формирует и отправляет запросы, парсит ответы и проверяет каждый блок на фактические противоречия с помощью LLM, исправляя нарушения в цикле. Итоговый объект FileGenerationOutcome содержит проверенные секции, готовые к сохранению — вызывающему не нужно повторять верификацию. За счёт этого остальная система получает надёжный инструмент сквозной регенерации документации, скрывающий детали лимитов модели и логики промптов.

## Что делает

Подсистема владеет полным циклом генерации документации для группы файлов: сбор документации зависимостей (collectDependencyDocs), разбиение исходного кода на чанки (planWriterChunks), формирование структурированных запросов (buildFileWriteRequest), парсинг ответов LLM (parseFileWriteResponse), факт-чекинг с циклом «ремонт — перепроверка» (verifyChunkFacts и buildRepairRequest). После обработки чанков она проверяет существующие блоки на соответствие документации зависимостей (verifyBlocksAgainstDeps) и атомарно записывает отладочный снимок (writeGenerationDebug). Отдельно, утилита compactChunkCallers уменьшает дублирование тел вызывающих функций, отдавая приоритет вызывающим с runtimeEvidence — это позволяет оптимизировать размер промпта перед генерацией.

## От чего зависит

Пайплайн опирается на другие подсистемы за готовыми входными данными: граф изменений и список затронутых файлов/секций приходят от подсистемы «Граф зависимостей и влияние изменений»; бюджет токенов и термины — от «Конфигурации проекта»; runtimeEvidence для вызывающих — от «Построения runtime-контекста из литералов». Структурную валидацию (длину блоков, ссылки) пайплайн не выполняет самостоятельно — она лежит на подсистеме валидации, которая запускается после генерации. Сам пайплайн не строит граф зависимостей, не вычисляет изменения и не сохраняет документацию на диск — эти задачи остаются за вызывающим фасадом сервиса.

## Кто и как использует

generateFileGroup собирает документацию зависимостей и разбивает исходные файлы на чанки через planWriterChunks. Каждый чанк обрабатывается параллельно: запрос к LLM строится buildFileWriteRequest, ответ парсится в FileWriteResult через parseFileWriteResponse, затем verifyChunkFacts проверяет блоки на фактические противоречия и, при обнаружении, запускает ремонт (buildRepairRequest) с повторной верификацией. Результаты чанков сливаются — более поздние чанки перезаписывают одноимённые блоки. Существующие блоки, не попавшие в генерацию, проходят проверку на соответствие документации зависимостей через verifyBlocksAgainstDeps. В конце writeGenerationDebug записывает отладочный снимок прогона.

## Чего не делает

Пайплайн не сохраняет сгенерированную документацию на диск — возвращает FileGenerationOutcome. planWriterChunks разбивает файлы по границам top-level сущностей и не дробит отдельные сущности; если одна сущность превышает лимит токенов, она не будет разбита, и чанк может выйти за лимиты модели. collectDependencyDocs ограничивает суммарный объём документации зависимостей константами DEP_DOCS_TOTAL_CAP и DEP_DOC_FILE_CAP, молча отбрасывая данные сверх лимита. verifyBlocksAgainstDeps возвращает только идентификаторы секций без нарушений — вызывающий не узнает, какие блоки и в чём противоречат зависимостям. Ошибки файловой системы при записи отладочного снимка пробрасываются наверх без обработки.
