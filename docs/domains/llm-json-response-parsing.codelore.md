# Разбор JSON-ответов LLM с повтором запроса

## Состав

- [complete-and-parse](../../src/llm/complete-and-parse.codelore.md) — Обеспечивает устойчивость вызова LLM к невалидному JSON в ответе: повторяет запрос с обратной связью, пока парсинг не удастся или не кончатся попытки.
- [json](../../src/llm/json.codelore.md) — Точка входа для парсинга JSON-ответа LLM.

## Зачем это нужно

Подсистема даёт остальной системе надёжный способ получить структурированный JSON-объект из текстового ответа языковой модели. Модель может вернуть невалидный JSON с Markdown-фенсами, экранированными обратными кавычками или другими артефактами — подсистема исправляет известные искажения и парсит ответ. Если разбор не удался, она не просто сигнализирует об ошибке, а повторяет запрос к модели, сообщая ей, что именно пошло не так — это повышает шанс получить корректный JSON без вмешательства вызывающего кода. В итоге наружу выходит либо объект, либо CodeloreError с кодом INVALID_LLM_RESPONSE, освобождая остальную систему от реализации логики повторов и обработки JSON-артефактов.

## Что делает

Подсистема принимает запрос к LLM, функцию вызова complete и лимит повторов. completeAndParse вызывает complete с исходными сообщениями и передаёт полученный текст в parseJsonObject. Тот снимает внешний Markdown-фенс, парсит JSON, при неудаче применяет repairKnownLlmEscapes — исправление трёх известных артефактов — и пробует распарсить снова. Итоговое значение обязательно должно быть объектом. Если обе попытки сорвались, выбрасывается CodeloreError с кодом INVALID_LLM_RESPONSE. completeAndParse ловит эту ошибку и, пока лимит не исчерпан, добавляет в историю assistant-сообщение с провальным ответом и user-сообщение с описанием ошибки, после чего снова вызывает модель. Ошибки провайдера, не связанные с разбором, и исчерпание попыток записываются в отладку и пробрасываются наверх. readOptionalString позволяет безопасно забрать опциональные строки из полученного объекта: нет поля — возвращает undefined, поле есть, но не строка — выбрасывает INVALID_LLM_RESPONSE.

## От чего зависит

Подсистема полагается на единый формат ошибок — CodeloreError с кодом INVALID_LLM_RESPONSE — как на общий сигнал о неудачном разборе, понятный всем верхним слоям. Вызов модели она выполняет не сама, а через переданную извне функцию complete, поэтому сетевые таймауты, ошибки транспорта и квоты провайдера остаются за пределами её зоны ответственности — она лишь пробрасывает их после записи в отладку. Отладочный вывод идёт через предоставленный обратный вызов writeDebug; свои ошибки этот вызов не обрабатывает. Подсистема не валидирует внутреннюю структуру разобранного JSON дальше проверки, что результат — объект.

## Кто и как использует

Вызывающий код передаёт в completeAndParse запрос с сообщениями, функцию complete и лимит попыток. completeAndParse вызывает complete с запросом, получает текстовый ответ и отдаёт его в parseJsonObject. Тот последовательно снимает внешний Markdown-фенс, парсит JSON, при провале — чинит ответ через repairKnownLlmEscapes и парсит снова. Если результат — объект, completeAndParse возвращает его вызывающему коду. Если parseJsonObject выбросил INVALID_LLM_RESPONSE, completeAndParse проверяет лимит: если попытки ещё есть, создаёт новую копию запроса с дополненной историей — assistant-сообщение содержит провальный ответ, user-сообщение описывает ошибку парсинга, — и повторяет цикл. Исходный запрос остаётся неизменным. При исчерпании попыток или не-INVALID ошибке провайдера происходит запись отладки, и ошибка пробрасывается. После успешного разбора readOptionalString извлекает опциональные строковые поля: отсутствующее поле даёт undefined, значение не-строка вызывает выброс INVALID_LLM_RESPONSE.

## Чего не делает

Повторы выполняются только для ошибок разбора с кодом INVALID_LLM_RESPONSE; любая другая ошибка провайдера или ошибка парсинга с иным кодом сразу пробрасывается вызывающему коду после записи отладки. Лимит попыток жёсткий, после его исчерпания никакого запасного объекта не возвращается — только ошибка. repairKnownLlmEscapes исправляет три известных LLM-артефакта: экранированные обратные кавычки, \$ и \\. readOptionalString извлекает только строковые поля: отсутствующее поле даёт undefined, значение не-строка вызывает выброс INVALID_LLM_RESPONSE. Подсистема не проверяет смысловую корректность полей объекта — только что результат является объектом. Ошибки самого writeDebug не перехватываются — отладка считается best-effort.
