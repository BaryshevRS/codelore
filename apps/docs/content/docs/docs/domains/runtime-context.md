title: Построение runtime-контекста из литералов

## Состав

* [ast-helpers](/docs/src/context/ast-helpers) — Отсеивает строковые литералы, находящиеся внутри `import` или `export` деклараций.
* [ast-hit-filter](/docs/src/context/ast-hit-filter) — Фильтрует результаты ripgrep-поиска, оставляя только те строковые литералы, которые являются реальными вызовами в коде, а не частью импортов, типов, JSDoc или контекстных типов.
* [enclosing-resolver](/docs/src/context/enclosing-resolver) — Преобразует отфильтрованный ripgrep-хит в `RuntimeHit` с идентификатором сущности кода, в которой находится литерал.
* [literal-extractor](/docs/src/context/literal-extractor) — Выделяет строковые литералы в заданном диапазоне исходного кода для последующего поиска по проекту в процессе построения runtime-контекста.
* [ripgrep-runner](/docs/src/context/ripgrep-runner) — Поиск точных вхождений строки в исходных файлах TypeScript/JavaScript проекта через ripgrep.
* [runtime-context-builder](/docs/src/context/runtime-context-builder) — Собирает runtime-контекст для сущности кода: находит все вхождения строковых литералов из её исходного кода в проекте и возвращает структурированные попадания.

**Используется в:** [Пайплайн генерации документации файлов](/docs/docs/domains/llm-generation-pipeline#пайплайн-генерации-документации-файлов)

## Зачем это нужно

Строит для сущности кода карту всех вхождений её строковых литералов в других сущностях проекта, отсеивая технические использования. Каждый хит разрешается до содержащей его сущности. Карта позволяет системе анализировать неявные связи между сущностями через строковые константы, используемые в рантайме.

## Что делает

Подсистема владеет полным циклом: извлекает строковые литералы и no-substitution template literals из исходного кода, отфильтровывает технические (импорты, типы, JSDoc, контекстные типы) с помощью функций из ast-helpers, запускает ripgrep для поиска по проекту, фильтрует найденные совпадения через AstHitFilter, разрешает их до содержащей сущности через resolveEnclosing и определяет синтаксическую роль. Возвращает массив RuntimeHit и список литералов без валидных вхождений.

## От чего зависит

Зависит от внешнего инструмента ripgrep (через searchLiteral) для точного поиска строковых совпадений. Использует TypeScript Compiler API для анализа AST, загрузки исходных файлов и определения контекстных типов. Не реализует собственный полнотекстовый поиск, не управляет конфигурацией TS-проекта и не инвалидирует кэш SourceFile при изменениях на диске.

## Кто и как использует

Точка входа buildRuntimeContext получает сущность кода и её SourceFile. extractLiterals обходит AST и собирает строковые литералы и no-substitution template literals, отсеивая технические. Для каждого уникального литерала searchLiteral запускает ripgrep с --fixed-strings, исключая исходный файл. Каждый raw-хит обрабатывается AstHitFilter: загружает файл, парсит AST и отбрасывает вхождения внутри импортов, JSDoc, type-аннотаций или контекстных типов. Прошедшие фильтр хиты resolveEnclosing преобразует в RuntimeHit: находит ближайшую объемлющую сущность кода, вычисляет синтаксическую роль через computeSyntaxRole и отбрасывает самоссылки. Результат — массив RuntimeHit и список литералов без валидных вхождений.

## Чего не делает

Не фильтрует require() — проверяет только import/export декларации. Не обрабатывает однострочные и блочные комментарии — только JSDoc. Пропускает литералы внутри TypeReference и ArrayType, так как isInsideTypeNode проверяет только LiteralTypeNode. Контекстный тип не распознаётся в return и других неявных позициях. Определяет только синтаксическую роль, а не семантическое назначение. Не инвалидирует кэш SourceFile при изменениях на диске; ошибки парсинга файла глотаются без логирования. Ищет только строковые литералы и no-substitution template literals. Самоссылки отбрасываются. Поиск только точный — ripgrep запускается с --fixed-strings, регулярные выражения не поддерживаются.
