title: AstHitFilter
---

## Зачем это нужно

Фильтрует результаты ripgrep-поиска, оставляя только те строковые литералы, которые являются реальными вызовами в коде, а не частью импортов, типов, JSDoc или контекстных типов.

## Что делает

* Не выполняет поиск — получает уже найденные ripgrep-совпадения от `searchLiteral`.
* Не определяет синтаксическую роль литерала — делегирует `computeSyntaxRole`.
* Не управляет кэшем SourceFile — кэширует только результат загрузки файла, не инвалидирует его при изменениях на диске.
* Не обрабатывает ошибки парсинга файла — при неудаче возвращает `null` без логирования.

## На что можно положиться

* Для каждого `RipgrepHit` возвращает либо `FilteredHit` с корректным `offset`, либо `null`.
* `offset` в `FilteredHit` равен `node.getStart()` — началу узла в файле, а не позиции совпадения.
* Кэш `sourceFiles` никогда не обновляется после первой загрузки файла — если файл изменился на диске, используется старая версия.
* При отсутствии файла на диске или ошибке парсинга возвращает `null` без исключения.

## От чего зависит

* `ts-morph` — парсинг TypeScript-файлов и навигация по AST.
* [`src/context/ast-helpers.ts`](/docs/src/context/ast-helpers) — вспомогательные функции для проверки контекста литерала (`isInsideImportExport`, `isInsideJsDoc`, `isInsideTypeNode`, `hasLiteralContextualType`).
* [`src/context/ripgrep-runner.ts`](/docs/src/context/ripgrep-runner) — тип `RipgrepHit`, результаты поиска.

## Кто и как использует

1. [`buildRuntimeContext`](/docs/src/context/runtime-context-builder#buildruntimecontext) (`src/context/runtime-context-builder.ts`) создаёт экземпляр `AstHitFilter` с переданным `Project`.
2. Для каждого уникального литерала, извлечённого из целевой сущности, вызывается `searchLiteral` (ripgrep).
3. Каждый найденный `RipgrepHit` передаётся в `AstHitFilter.filter`.
4. Если фильтр возвращает `FilteredHit` — он добавляется в итоговый массив `hits`. Если `null` — литерал считается неразрешённым.

## Чего не делает

* Кэш `sourceFiles` не инвалидируется — при изменении файла на диске между вызовами `filter` используется старая версия AST.
* Не обрабатывает ошибки парсинга — при неудаче `getSourceFile` возвращает `null` без логирования, что может скрыть проблемы с файлом.
* Не поддерживает другие типы литералов (числовые, шаблонные строки с выражениями) — фильтруются только строковые литералы и шаблонные литералы без подстановок.

## Как менять и что проверять

1. Если добавляется новый тип литерала (например, числовые) — расширить `isAcceptedLiteralNode` и проверить, что `hasLiteralContextualType` корректно обрабатывает новый тип.
2. Если меняется логика кэширования `sourceFiles` — убедиться, что [`buildRuntimeContext`](/docs/src/context/runtime-context-builder#buildruntimecontext) не теряет контекст между вызовами `filter`.
3. Если добавляется новый критерий отсева — добавить соответствующую функцию в [`src/context/ast-helpers.ts`](/docs/src/context/ast-helpers) и включить её в `isAcceptedLiteralNode`.
4. Если меняется формат `RipgrepHit` — обновить `filter` и проверить, что `FilteredHit` всё ещё корректен.
