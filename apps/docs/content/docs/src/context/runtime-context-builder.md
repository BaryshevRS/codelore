## Зачем это нужно

Собирает runtime-контекст для сущности кода: находит все вхождения строковых литералов из её исходного кода в проекте и возвращает структурированные попадания.

## Что делает

* Загружает исходный файл целевой сущности и извлекает строковые литералы через extractLiterals.
* Делегирует поиск литералов в проекте searchLiteral, фильтрацию попаданий — AstHitFilter, разрешение контекста — resolveEnclosing.
* Исключает из поиска исходный файл целевой сущности.
* Возвращает список неразрешённых литералов, для которых не найдено ни одного валидного попадания.

## На что можно положиться

* Если целевая сущность не найдена в codeIndex, функция возвращает пустой результат без ошибки.
* Если исходный файл не удалось загрузить (loadSource вернул null), функция возвращает пустой результат без ошибки.
* Если extractLiterals не вернул ни одного литерала, функция возвращает пустой результат без ошибки.
* Поиск литералов выполняется по уникальным значениям: дубликаты по значению исключаются перед вызовом searchLiteral.
* Для каждого литерала, не давшего ни одного валидного попадания, литерал заносится в unresolvedLiterals.
* resolveSingleHit возвращает null, если разрешённая сущность совпадает с целевой (самоссылка).

## От чего зависит

* extractLiterals ([src/context/literal-extractor.ts](/docs/src/context/literal-extractor)) — извлечение строковых литералов из исходного файла.
* searchLiteral ([src/context/ripgrep-runner.ts](/docs/src/context/ripgrep-runner)) — поиск литералов в проекте через ripgrep.
* AstHitFilter ([src/context/ast-hit-filter.ts](/docs/src/context/ast-hit-filter)) — верификация, что найденное ripgrep-совпадение является реальным строковым литералом в AST.
* resolveEnclosing ([src/context/enclosing-resolver.ts](/docs/src/context/enclosing-resolver)) — преобразование отфильтрованного хита в RuntimeHit с идентификатором сущности-контейнера.

## Кто и как использует

1. Извлечь уникальные строковые литералы из целевой сущности с помощью extractLiterals.
2. Для каждого уникального литерала выполнить поиск в проекте через searchLiteral (ripgrep), исключив исходный файл целевой сущности.
3. Отфильтровать найденные ripgrep-попадания через AstHitFilter, чтобы подтвердить, что они являются реальными вхождениями литерала.
4. Для прошедших фильтр разрешить контекст через resolveEnclosing — получить идентификатор сущности, содержащей литерал.
5. Собрать результат: структурированные попадания и список литералов, для которых не найдено ни одного валидного попадания.

**Контекст вызова**: функция вызывается из [`src/llm/file-pipeline.ts`](/docs/src/llm/file-pipeline) при генерации документации для обогащения контекста runtime-попаданиями.

## Чего не делает

* searchLiteral исключает `node_modules`, `dist`, `build`, `.codelore`, `coverage`. Литералы в этих директориях не будут найдены.
* AstHitFilter кэширует SourceFile и не обновляет при изменениях на диске — результаты могут быть устаревшими, если файл изменился после загрузки.
* resolveEnclosing возвращает null для самоссылок — если литерал используется в той же сущности, он не попадёт в hits, а попадёт в unresolvedLiterals.
* extractLiterals фильтрует литералы короче 4 символов — короткие литералы (например, `id`, `ok`) не будут обработаны.

## Как менять и что проверять

* Если меняется фильтрация литералов в extractLiterals (например, изменяется MIN\_LITERAL\_LENGTH), проверьте, что набор литералов, передаваемых в searchLiteral, соответствует ожиданиям. Убедитесь, что unresolvedLiterals корректно обновляется.
* Если меняется логика resolveEnclosing (например, прекращается возврат null для самоссылок), это приведёт к включению самоссылок в hits, что нарушит контракт buildRuntimeContext. Проверьте downstream, ожидающие отсутствия самоссылок.
