title: extractLiterals
---

## Зачем это нужно

Выделяет строковые литералы в заданном диапазоне исходного кода для последующего поиска по проекту в процессе построения runtime-контекста.

## Что делает

* Не обрабатывает литералы внутри `import`, `export`, JSDoc, type-аннотаций и литералов с контекстным типом — делегирует фильтрацию функциям из `ast-helpers.ts`.
* Не включает другие типы литералов (числа, булевы) — только строковые и no-substitution template literal.
* Не пересекает границы файла — работает только в пределах переданного `SourceFile`.
* Не ищет семантические совпадения — возвращает только значение, синтаксическую роль и позицию.

## На что можно положиться

* Длина каждого отфильтрованного литерала ≥ 4 символов (константа `MIN_LITERAL_LENGTH`).
* Один литерал на одну позицию (дедупликация по комбинации `offset:value`).
* Возвращает пустой массив, если в диапазоне нет подходящих литералов.
* Порядок результатов — обход в глубину AST (`forEachDescendant`).

## От чего зависит

* [`computeSyntaxRole`](/docs/src/context/ast-helpers#computesyntaxrole) (`src/context/ast-helpers.ts`) — определяет синтаксическую роль литерала (аргумент вызова, инициализатор свойства и т.д.).
* Остальные вспомогательные функции фильтрации (проверка на импорты/экспорты, JSDoc, type-узлы, контекстный тип) — [`src/context/ast-helpers.ts`](/docs/src/context/ast-helpers).

## Кто и как использует

Вызывается из [`buildRuntimeContext`](/docs/src/context/runtime-context-builder#buildruntimecontext) с целевым `SourceFile` и `target.range`. Если `extractLiterals` возвращает пустой массив, [`buildRuntimeContext`](/docs/src/context/runtime-context-builder#buildruntimecontext) немедленно возвращает `{ hits: [], unresolvedLiterals: [] }`. В противном случае для каждого уникального значения (через `uniqueValues`) запускается поиск по проекту (`searchLiteral`) с исключением файла цели, а результаты фильтруются через `resolveHitsForLiteral`.

## Чего не делает

* Фильтр `hasLiteralContextualType` работает только для выражений — литералы в позициях без контекстного типа (например, `return "literal"`) не отсеиваются.
* Минимальная длина `MIN_LITERAL_LENGTH = 4` — короткие строки игнорируются, что может пропустить значимые контракты (например, `"id"`).
* Дедупликация по `offset:value` — один и тот же литерал на разных позициях учитывается повторно, хотя значение уже обрабатывалось.

## Как менять и что проверять

1. Изменение `MIN_LITERAL_LENGTH` — повлияет на количество извлечённых литералов, а значит на число поисков по проекту. Проверить тюнинг производительности в тестах [`buildRuntimeContext`](/docs/src/context/runtime-context-builder#buildruntimecontext).
2. Добавление нового условия в `isAcceptableLiteral` — может скрыть литералы, которые ожидаются в `resolveHitsForLiteral`. Проверить итоговые `RuntimeHit` через прогон интеграционного теста (связка `extractLiterals` → `searchLiteral`).
3. Изменение дедупликации (например, снятие `offset` из ключа) — приведёт к потере одного и того же значения на разных позициях. Проверить, что `directUsages` не потеряли срабатываний.
