# file-dag.ts

## Зачем это нужно

Служит графовой утилитой для упорядочивания обработки файлов при генерации документации: связывает построитель DAG и планировщик волн в единый конвейер, который соблюдает порядок зависимостей и схлопывает циклы.

## Что делает

- Экспортирует тип `FileDag` как общую структуру данных между `buildFileDag` и `generationWaves`, через которую передаётся информация о присутствии файла и его зависимостях.
- Устанавливает конвенцию модуля: присутствие файла в DAG (проверка `dag.has(file)`) — это фильтр для включения в любые последующие вычисления, и эта проверка применяется единообразно во всех точках входа.
- Гарантирует детерминированный вывод через единообразную сортировку на каждом уровне: соседи в `stronglyConnectedComponents`, группы по первому файлу, волны по возрастанию уровня.

## На что можно положиться

- Все экспортируемые функции разделяют конвенцию: файлы, отсутствующие в `code.fileToEntities`, невидимы для модуля и не попадают ни в граф, ни в волны.
- DAG, построенный `buildFileDag`, — единственный источник истины о присутствии файлов; `generationWaves` фильтрует свой вход через `dag.has(file)` и не выполняет собственной проверки `code.fileToEntities`.
- Порядок вывода детерминирован во всех точках входа: соседи сортируются в `stronglyConnectedComponents`, группы внутри волны — по первому файлу, волны — по возрастанию уровня.

## Чего не делает

Модуль ограничивает входные данные до `code.fileToEntities`: вершины графа создаются итерацией `Object.keys(code.fileToEntities)` в `buildFileDag`, и та же проверка `dag.has(file)` действует как единственный шлюз видимости в `generationWaves`. Три причины отбрасывания рёбер — отсутствующая в `code.entities` сущность, самозависимость и файл вне графа — объединены в одно молчаливое условие `depEntity && depEntity.path !== entity.path && dag.has(depEntity.path)` в `buildFileDag`, и модуль не различает их в выводе. Тип `FileDag` отдан наружу как `Map<string, Set<string>>`, и оба экспортируемых потребителя вынуждены разделять ту же конвенцию присутствия через `dag.has`; формат `generationWaves` — `string[][][]`, где внешний массив индексируется номером волны, средний — SCC-группами, внутренний — отсортированными путями.

# buildFileDag

```ts
buildFileDag(code: CodeIndex): FileDag
```

## Зачем это нужно

Строит файловый граф зависимостей, который служит основой для планирования волн и документирования зависимостей, транслируя прямые зависимости сущностей в файловые рёбра.

## Что делает

- Создаёт одну вершину для каждого файла из `code.fileToEntities` с пустым множеством зависимостей, формируя множество вершин графа за один проход.
- Обходит все сущности из `code.entities` и добавляет файлы их прямых зависимостей в множество владельца, применяя три фильтра в одном условии: сущность должна существовать (`depEntity`), путь должен отличаться от пути владельца (`depEntity.path !== entity.path`), файл зависимости должен быть в графе (`dag.has(depEntity.path)`).
- Возвращает `Map<string, Set<string>>`, где ключи — пути файлов, значения — множества файлов, от которых они напрямую зависят; граф всегда содержит все файлы из `code.fileToEntities`, даже если у них нет зависимостей.

## На что можно положиться

- Возвращаемый граф содержит ровно те же ключи, что и `code.fileToEntities`; если объект пуст, возвращается пустой `Map`.
- Ни один файл не указывает сам на себя: проверка `depEntity.path !== entity.path` отбрасывает самозависимости.
- Зависимости на файлы вне графа молча отбрасываются: проверка `dag.has(depEntity.path)` гарантирует, что в множестве зависимостей оказываются только файлы, присутствующие в `code.fileToEntities`.
- Зависимости, чья сущность не найдена в `code.entities`, молча отбрасываются: проверка `depEntity` отсекает невалидные идентификаторы.
- Граф не мутирует входные данные: возвращается новый `Map` с новыми `Set`.

## Кто и как использует

Три потребителя получают DAG и сразу сужают или преобразуют его: `generationWaves` (src/graph/file-dag.ts) фильтрует входной список через `files.filter((file) => dag.has(file))` и далее группирует файлы в волны; `collectDependencyDocs` (src/llm/file-pipeline.ts) перебирает `dag.get(file) ?? []` для каждого файла группы, копит внешние зависимости в `Set<string> depFiles` и затем строит `DependencyDoc` под лимитом `DEP_DOCS_TOTAL_CAP` через `JSON.stringify(doc.sections).length`; `renderGraphHtml` (src/cli/render-graph.ts) и `renderGraphTree` (src/cli/render-graph.ts) распределяют узлы по волнам через `byWave = new Map<number, FileNode[]>()` и сортируют их через `sort((left, right) => left.file.localeCompare(right.file))`, после чего первая превращает рёбра в формат Cytoscape.js через `node.deps.map((dep) => ...)`, а вторая — в текстовое дерево с префиксом `←`.

## Чего не делает

Функция всегда возвращает полный граф: итерация `Object.keys(code.fileToEntities)` создаёт вершину для каждого ключа через `dag.set(file, new Set())`, поэтому файлы без зависимостей всё равно попадают в результат с пустым множеством. Чтение из `code` ограничено двумя полями — `fileToEntities` для вершин и `entities` для зависимостей; другие поля `CodeIndex` игнорируются. Три причины отбрасывания (отсутствующая сущность, самозависимость, файл вне графа) слиты в одно молчаливое условие `depEntity && depEntity.path !== entity.path && dag.has(depEntity.path)`, и функция не делает различий между ними в выводе.

## Как менять и что проверять

1. Полнота графа обеспечивается парой `for (const file of Object.keys(code.fileToEntities))` + `dag.set(file, new Set())`: первая часть перечисляет ключи, вторая создаёт вершину с пустым множеством.
2. Безопасный порядок проверок в `depEntity && depEntity.path !== entity.path && dag.has(depEntity.path)`: `depEntity` стоит первым и защищает обращение к `depEntity.path` во второй части коротким замыканием.

# generationWaves

```ts
generationWaves(code: CodeIndex, files: string[]): string[][][]
```

## Зачем это нужно

Вычисляет минимальное расписание волн для обработки набора файлов, гарантируя, что зависимости обрабатываются раньше зависимых, а циклы — в одной волне.

## Что делает

- Строит DAG через `buildFileDag`, затем ограничивает область файлами, присутствующими в графе (фильтр `dag.has(file)`), формируя множество `scope`.
- Разбивает файлы из `scope` на компоненты сильной связности через `stronglyConnectedComponents`, получая массив групп, где каждая группа — множество файлов, связанных циклами.
- Присваивает каждой SCC уровень, равный максимальному уровню её зависимостей плюс один (SCC без зависимостей получают уровень 0), используя мемоизацию через массив `levels` для избежания повторных вычислений.
- Возвращает волны как массив массивов групп файлов, где каждая группа — отсортированная SCC, а волны упорядочены по возрастанию уровня; группы внутри волны дополнительно сортируются по первому файлу через `left[0].localeCompare(right[0])`.

## На что можно положиться

- Если файл A нециклически зависит от файла B, индекс волны A строго больше индекса волны B.
- Все файлы одной SCC находятся в одной волне: компоненты сильной связности не разделяются между волнами.
- Файлы, отсутствующие в DAG, исключаются из вывода: фильтр `dag.has(file)`; если после фильтра область пуста, возвращается пустой массив волн.
- Группы внутри волны отсортированы по первому файлу: `left[0].localeCompare(right[0])`.
- Волны упорядочены по возрастанию уровня: волна с индексом 0 содержит SCC без зависимостей, последующие волны содержат SCC, зависящие от предыдущих.

## От чего зависит

`buildFileDag` (src/graph/file-dag.ts) передаёт функции готовый `FileDag`; `stronglyConnectedComponents` (src/graph/file-dag.ts) возвращает массив SCC в порядке обхода Tarjan'а, который локально превращается в `Map<string, number> groupOfFile` и в `Array<number> levels` для мемоизации уровня. `stronglyConnectedComponents` итеративен — он работает через массив `work` и `stack: string[]` для вершин SCC; функция `levelOf` остаётся рекурсивной и опирается на `levelOf(depGroup) + 1` для обхода зависимостей между SCC.

## Кто и как использует

`renderGraphHtml` и `renderGraphTree` (src/cli/render-graph.ts) числятся в списке вызывающих; обе функции распределяют узлы по волнам через `byWave = new Map<number, FileNode[]>()` и сортируют узлы внутри волны через `sort((left, right) => left.file.localeCompare(right.file))`. В `renderGraphHtml` волны превращаются в координатную сетку Cytoscape.js с `y: (maxWave - node.wave) * 170` и `x: (column - (rowMates.length - 1) / 2) * 230`; в `renderGraphTree` — в текстовое дерево с заголовком `wave ${wave}` и префиксом `←` для каждой зависимости.

## Чего не делает

Сортировка групп внутри волны опирается на первый файл SCC: `left[0].localeCompare(right[0])` — порядок SCC определяется только первым путём, а не составом всей компоненты. Область SCC сужается до входного списка: `new Set(files.filter((file) => dag.has(file)))` отбрасывает файлы без записей в `code.fileToEntities`. `levelOf` помечает `levels[groupIndex] = 0` перед обходом зависимостей и перезаписывает его `levels[groupIndex] = level` в конце; промежуточное значение служит маркером «в обработке» для рекурсивных вызовов и опирается на уже ацикличную решётку SCC.

## Как менять и что проверять

1. Область SCC ограничена входным списком: `new Set(files.filter((file) => dag.has(file)))` — `dag.has(file)` отсекает файлы без записей в `code.fileToEntities`.
2. Уровень SCC вычисляется максимумом зависимостей плюс один: `level = Math.max(level, levelOf(depGroup) + 1)` — `Math.max` фиксирует правило, что SCC без зависимостей получает уровень 0.
3. Сортировка групп опирается на `left[0].localeCompare(right[0])` — компаратор сравнивает только `left[0]`, не учитывая остальные элементы SCC.
4. Мемоизация в `levelOf` использует `levels[groupIndex] = 0` как маркер «в обработке» и `levels[groupIndex] = level` как финальное значение.
